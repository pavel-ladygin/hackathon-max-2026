# MAX Together

**Афиша мероприятий и совместный выбор досуга в MAX.** Один участник создаёт комнату и приглашает другого. Оба получают общий список подходящих событий, голосуют независимо и видят совпадение, когда положительно оценили одно мероприятие. Из карточки совпадения можно перейти на сайт продажи билетов.

## Основной сценарий

1. Пользователь **A** открывает мини-приложение из бота MAX, выбирает город и создаёт комнату.
2. Задаёт параметры досуга и отправляет приглашение **B** через MAX.
3. B открывает ссылку, входит в комнату и задаёт собственные предпочтения.
4. Сервис формирует общий список мероприятий. Участники независимо голосуют за одни и те же события.
5. Два положительных голоса за одно событие создают **мэтч**. Оба участника могут открыть карточку мероприятия.
6. Кнопка билета переводит на сайт организатора или билетного сервиса. **MAX Together не продаёт билеты и не подтверждает покупку.**

Кроме комнат доступны афиша, поиск, фильтры, карточки мероприятий и сохранённые события. Приоритетный сценарий для проверки — **комната → приглашение → голосование → мэтч → переход к билету**.

## Запуск за одну команду

**Требуется:** Docker Engine / Docker Desktop и Docker Compose v2. Go, Node.js и PostgreSQL на хост устанавливать не нужно.

Из корня репозитория выполните:

```bash
docker compose --env-file .env.submission.example up -d --build
```

Команда поднимает PostgreSQL, применяет миграции, загружает **два подготовленных события**, запускает Go API и frontend. Обращения к внешним поставщикам при этом выключены.

| Компонент | Адрес / порт | Назначение |
| --- | --- | --- |
| Mini App (локально) | <http://localhost:8081> | Веб-интерфейс; без настоящей MAX-сессии защищённый сценарий не авторизуется |
| API | <http://localhost:8080/api/v1> | Основная бизнес-логика |
| Readiness API | <http://localhost:8080/api/v1/health/ready> | Готовность backend и его зависимостей |
| Frontend health | <http://localhost:8081/health> | Доступность frontend |
| PostgreSQL | `127.0.0.1:5432` | Локальная база проверочного стенда |

Проверьте готовность:

```bash
curl --fail --connect-timeout 5 --max-time 10 --retry 12 --retry-delay 2 --retry-connrefused http://localhost:8080/api/v1/health/ready
curl --fail --connect-timeout 5 --max-time 10 --retry 12 --retry-delay 2 --retry-connrefused http://localhost:8081/health
```

Оба запроса должны вернуть **HTTP 200**. По умолчанию база называется `max_together_submission`, а Compose-проект — `max-together-submission`. Если порты заняты, создайте собственный env-файл из `.env.submission.example`, измените соответствующие `*_PORT` и укажите новый файл в `--env-file`.

**Остановить / запустить повторно:**

```bash
docker compose --env-file .env.submission.example down
docker compose --env-file .env.submission.example up -d --no-build
```

Команда `down` сохраняет том PostgreSQL. Для полного сброса **только локального проверочного стенда** используйте `docker compose --env-file .env.submission.example down -v`: данные его базы будут удалены.

## Проверка решения

### В настоящем MAX

Откройте [бота](https://max.ru/t255_hakaton_max_bot) в мобильном и веб-клиенте MAX и выполните сценарий **с двумя разными аккаунтами A и B**:

1. A открывает Mini App, находит мероприятие в афише, открывает карточку и создаёт комнату.
2. A задаёт параметры и отправляет ссылку через MAX; B открывает её и вступает в нужную комнату.
3. Участники задают собственные предпочтения и видят общий пул.
4. A и B положительно оценивают одно событие. Оба получают результат совпадения.
5. Открывают событие и переходят по билетной ссылке; затем повторно открывают комнату и проверяют сохранение результата.
6. Дополнительно проверьте пустой пул и сообщения об ошибке. Основной сценарий должен быть доступен и в MAX Web, и в мобильном MAX.

Для проверки живого MAX нужны доступный по HTTPS Mini App, настроенный бот и актуальные подписанные `initData` каждого пользователя. Входа по постоянному логину и паролю нет. Для HTTP-проверки в MAX Web получите свежий `access_token` из ответа `POST /api/v1/auth/max/bootstrap` во вкладке Network отдельно для A и B; не публикуйте запросы, HAR и токены.

Проверьте приглашение через доступные `shareMaxContent` / `shareContent`, запасной Web Share и копирование ссылки. Ссылка должна приводить B в нужную комнату; обычный браузер не даёт MAX-авторизацию.

### В локальном Docker-стенде

Для автономной HTTP-проверки нужны `curl`, Python 3 и запущенный стек из раздела выше. Полный [сценарий с готовыми командами для A и B](docs/LOCAL_HTTP_VERIFICATION.md) включает тестовые MAX-подписи, создание комнаты, вступление, настройку предпочтений, общий лайк и переход к билету.

| Проверка | Ожидаемое поведение |
| --- | --- |
| Readiness | API и frontend отвечают `200` |
| Афиша, поиск, карточка | Два подготовленных события доступны через обычные API-маршруты |
| Создание и вступление | A создаёт комнату; B вступает по токену приглашения |
| Голосование | Общий `like` одного события создаёт мэтч |
| Переход к билету | Возвращается тестовый URL на домене `.invalid`; реальной покупки нет |
| Повторный запуск | Комната и события сохраняются при `down` без `-v` |

Подробные контракты методов, параметры и ожидаемые ответы описаны в [`openapi/openapi.yaml`](openapi/openapi.yaml). Последовательность проверок собственного API — в [`DATA-API.yaml`](DATA-API.yaml).

## Архитектура

```text
                 MAX (бот + Mini App)
                          │
                 React / TypeScript
                          │
                       Go API
              ┌───────────┼───────────┐
              │           │           │
         Афиша/поиск    Комнаты     Сессии MAX
              │       Голоса/мэтч   и доступ
              └───────────┼───────────┘
                          │
                      PostgreSQL
                          ▲
               Нормализация событий
                          ▲
                 Адаптеры источников
                    KudaGo / Timepad
```

| Часть | Технологии и ответственность |
| --- | --- |
| [`frontend/`](frontend/) | React 19, TypeScript, Vite, MAX UI и адаптер MAX Bridge; каталог, комнаты, свайпы, карточки |
| [`backend/`](backend/) | Go, HTTP API, авторизация, бизнес-логика комнат и мэтча, фоновые обработчики |
| PostgreSQL | События, пользователи, комнаты, голоса, результаты и аналитика; `pgx` и миграции Goose |
| [`openapi/openapi.yaml`](openapi/openapi.yaml) | OpenAPI 3.1; источник генерируемых типов Go и TypeScript |
| [`compose.yaml`](compose.yaml) | Воспроизводимый проверочный стенд; импорт внешних событий выключен по умолчанию |
| [`compose.production.yaml`](compose.production.yaml) | Production-сервисы, синхронизация событий и ежедневные уведомления |
| [`compose.maintenance.yaml`](compose.maintenance.yaml) | Отдельное ручное восстановление постеров Timepad |

**Масштабирование по городам:** комнаты, голоса и мэтчи работают с единой моделью события. Для нового города требуется настроить покрытие источниками, сопоставление площадок/категорий и проверить качество данных; переписывать механику совместного выбора не нужно.

## Источники и тестовые данные

| Источник | Режим | Особенности |
| --- | --- | --- |
| KudaGo | Внешний API, включается отдельно | Актуальность и полнота зависят от поставщика |
| Timepad | Внешний API, включается отдельно | Требует `TIMEPAD_TOKEN`; при отсутствии доступа не участвует в импорте |
| [`backend/seed/submission.json`](backend/seed/submission.json) | Локальная проверка | **2 подготовленных события**: `source=submission-fixture`, `is_demo=false` |
| `go run ./cmd/seed` в `backend/` | Отдельная демозагрузка | **44 демонстрационных события** с `is_demo=true`; обычная выдача их исключает |

**Остальные внешние интеграции:** Backend проверяет подпись MAX `initData`; MAX Bridge передаёт данные входа и используется для отправки приглашений. MAX Bot API используется для уведомлений. Билетные ссылки открывают внешние сайты из allowlist; получение платежного подтверждения не реализовано. Карты используют дополнительную настройку API-ключа, если она включена в выбранной конфигурации. MAX и внешние поставщики не воспроизводятся локальным Docker-стендом; их работа проверяется отдельно в целевом окружении.

Внешние события приводятся к одной модели и сопоставляются по `source + external_id`. Сбой одного поставщика не должен останавливать синхронизацию остальных. Устаревшие записи деактивируются только после успешной синхронизации соответствующего источника.

В тестовом стенде дата событий рассчитывается относительно даты базы; тестовая билетная ссылка ведёт на зарезервированный домен `.invalid`. Подготовленные события **не являются подтверждением доступности реальных мероприятий или билетов**. Production-переходы используют только разрешённые домены билетных операторов.

Основные переменные (локальные параметры — в env-шаблонах; production — в `compose.production.yaml`):

| Переменная | Назначение |
| --- | --- |
| `APP_ENV`, `HTTP_ADDR`, `DATABASE_URL`, `LOG_LEVEL` | Режим и логи; Compose задаёт адрес `:8080` и собирает URL БД из `POSTGRES_*` |
| `MAX_BOT_TOKEN` | Проверка подписи MAX и работа бота; для живого MAX нужен действующий токен |
| `MAX_APP_URL`, `INVITE_URL_TEMPLATE`, `MAX_DEEP_LINK_TEMPLATE` | `MAX_APP_URL` нужен production-уведомлениям; HTTPS-шаблоны приглашений содержат `{token}` ровно один раз |
| `INVITE_ENCRYPTION_KEY`, `INVITE_ENCRYPTION_KEY_VERSION` | Стабильный base64-ключ шифрования приглашений (32 байта до кодирования) и его версия |
| `POSTGRES_PORT`, `BACKEND_PORT`, `FRONTEND_PORT` | Порты хоста локального стенда: 5432, 8080, 8081 |
| `VITE_MAX_APP_URL`, `VITE_TICKET_PROVIDER_ALLOWLIST`, `VITE_YANDEX_MAPS_API_KEY` | Параметры локальной сборки frontend; API проксируется через `/api/v1` |
| `TIMEPAD_TOKEN` | Необязательный доступ к Timepad |
| `EVENT_SYNC_RUN_ON_START` | Импорт при старте по умолчанию выключен; production Compose передаёт эту настройку |
| `TIMEPAD_MAX_REQUESTS_PER_MINUTE` | Лимит Timepad: по умолчанию 20 запросов в минуту |
| `EVENT_SYNC_INTERVAL` | Период синхронизации: submission-стенд — 60 минут; production и `.env.example` — 2 часа |
| `TICKET_PROVIDER_ALLOWLIST` | Допустимые домены перехода к билетам |
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` | Параметры production-БД |
| `BACKEND_IMAGE`, `FRONTEND_IMAGE` | Production-образы, привязанные к SHA релиза |
| `TRUSTED_PROXY_CIDRS`, `MAX_INIT_DATA_MAX_AGE` | Доверенные прокси и допустимый возраст MAX-авторизации |

Дополнительно могут потребоваться настройки карт (`YANDEX_MAPS_API_KEY` при сборке или `VITE_YANDEX_MAPS_API_KEY` на стороне frontend), адреса и таймауты источников. **Никакие production-секреты нельзя коммитить.** Рабочая production-конфигурация хранится на сервере отдельно от репозитория, например `/opt/worknet/.env.production` с правами `0600`. Не используйте тестовый env-файл для production.

## API и безопасность

Проверяемый API: **<https://worknet.team/api/v1>**. Описание методов — [`openapi/openapi.yaml`](openapi/openapi.yaml); список обязательных проверок — [`DATA-API.yaml`](DATA-API.yaml). Для оценки нужны доступный HTTPS-адрес, согласованный способ предоставления двух тестовых MAX-сессий и тестовые данные.

Mini App передаёт подписанную строку `initData` в `POST /api/v1/auth/max/bootstrap`. Backend проверяет подпись и срок действия по `MAX_BOT_TOKEN`, затем выдаёт случайный Bearer-токен на 24 часа. Токен хранится в памяти клиента. Неподписанная `initDataUnsafe` не используется как доказательство авторизации; `start_param` принимается только после проверки подписи. Каждый участник получает собственную сессию.

Приложение хранит идентификатор и необходимые поля профиля; координаты отправляются с согласия пользователя. Билетные URL проверяются по allowlist. Не включайте настоящие `initData`, токены и заголовки `Authorization` в логи, HAR-файлы и публичные материалы.

## Тесты и сборка

Основные команды разработки (PostgreSQL для интеграционных Go-тестов должен быть подготовлен, `TEST_DATABASE_URL` задан):

```bash
# В backend/
go run ./cmd/migrate
go test -p 1 ./...
go vet ./...
go build ./...

# В frontend/
npm ci
npm run check
npx playwright install chromium
npm run test:e2e
```

`npm run check` включает проверку политики источников, typecheck, lint, unit-тесты и production-сборку. В CI также выполняются проверки OpenAPI и генерации типов, сборка Docker и smoke-проверка локального стенда, тесты Nginx, Trivy и поиск секретов. Для воспроизведения контрактных тестов:

```bash
python -m pip install -r backend/tests/contract/requirements.txt
python -m unittest discover -s backend/tests/contract -v
```

Лимит Docker-сборки — 5 минут без первоначальной загрузки базовых образов. [Ранее записанные результаты и условия замера](docs/VERIFICATION_HISTORY.md) сохранены отдельно; новый замер сдаваемой версии не подтверждён.

Подробности дополнительных тестов, CI, секретов развёртывания и удаления старого recovery-контейнера — в [дополнительной инструкции](docs/DEVELOPMENT_AND_DEPLOY.md).

## Развёртывание и обслуживание

Production: <https://worknet.team>. Nginx завершает HTTPS и проксирует frontend/API; PostgreSQL не публикуется наружу. Скрипт `deploy/deploy.sh <40-character-commit-sha>` создаёт резервную копию PostgreSQL, обновляет образы, применяет миграции, выполняет smoke-проверки и предусматривает откат образов при ошибке. Реальные переменные находятся в приватном env-файле на сервере. Отдельно проверяются доступность MAX, TLS, домены билетов и состояние источников.

Импорт событий **не входит** в стандартный локальный запуск. Для включения KudaGo и, при наличии токена, Timepad:

```bash
docker compose --env-file .env.submission.example --profile live up -d event-sync
docker compose --env-file .env.submission.example logs --since=1h event-sync
```

При запуске `event-sync` импорт по умолчанию ждёт первого интервала: 60 минут в submission-стенде, 2 часа в production. В production немедленный импорт управляется `EVENT_SYNC_RUN_ON_START`; локальный Compose эту переменную не передаёт.

Восстановление постеров Timepad вынесено в maintenance-профиль, требует `TIMEPAD_TOKEN` и не запускается автоматически. Команда без `--apply` — предварительный просмотр:

```bash
docker compose --env-file .env.production -f compose.production.yaml -f compose.maintenance.yaml \
  --profile maintenance run --build --rm timepad-image-recovery
```

Для разового применения после имени сервиса добавьте `/app/backfill-timepad-posters --apply --limit 50`. Условия — в `backend/cmd/backfill-timepad-posters`. Не запускайте обслуживание одновременно с неподтверждённой миграцией или без проверенного резервного копирования.

## Ограничения и подготовка к сдаче

- Проверочный Docker-стенд не подключается к реальному MAX: подписи в HTTP-сценарии синтетические. Полный сценарий приглашения проверяется двумя настоящими аккаунтами в мобильном MAX и MAX Web.
- Качество live-каталога и наличие билетных ссылок зависят от KudaGo/Timepad; недоступность Timepad не заменяется выдуманными live-данными.
- Приложение фиксирует переход к билетному оператору, а не покупку. Тестовая ссылка `.invalid` не предназначена для оплаты.
- Постоянных логинов и паролей API нет. Способ выдачи проверяющим двух свежих MAX-сессий для production API необходимо согласовать.
- `DATA-API.yaml` содержит все девять смысловых элементов требований, но использует локальную версию структуры. Совместимость с машинной схемой платформы оценки необходимо подтвердить у организаторов.
