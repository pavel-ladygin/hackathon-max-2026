# KudaGo и городской фильтр Timepad

## Существующий автоматический режим

Основной `event-sync` сохраняет прежний цикл: KudaGo, затем Timepad при наличии токена и города, затем настроенные Generic sources. Интервал по умолчанию — 2h, `EVENT_SYNC_RUN_ON_START=false`. Полный обход страниц, нормализаторы, постеры, сохранение событий и provider-wide advisory locks остаются прежними. Новый SPB worker запускает тот же бинарный файл только для Timepad.

| Настройка | Default | Назначение |
|---|---|---|
| `KUDAGO_MAX_REQUESTS_PER_MINUTE` | `6` | Pacing 1–60/min; операторское значение, не официальная квота KudaGo |
| `EVENT_SYNC_PROVIDER` | пусто | Прежний набор источников; `timepad` выбирает только Timepad для отдельного worker |
| `TIMEPAD_UPSERT_ONLY` | `true` | Полный автоматический импорт без деактивации неувиденных событий на этапе проверки нового фильтра |
| `SPB_TIMEPAD_UPSERT_ONLY` | `true` | Та же настройка отдельно для SPB worker |

`TIMEPAD_MAX_REQUESTS_PER_MINUTE` остаётся 20, существующие page size/timeout/расписание сохраняются. Нового ограничения первыми N страницами нет. Изменение env требует пересоздания соответствующего контейнера; параметры не применяются горячим способом.

## Что известно о KudaGo 403

Из предоставленной оператором истории: запрос с VPS к `location=spb` получил HTTP 403 с короткой HTML-страницей nginx; исторические sync runs завершались failed до получения страниц. Это подтверждает отказ HTTP-доступа и отсутствие загруженной страницы. Это не устанавливает конкретное правило отказа, блокировку IP, состояние лицензии или первопричину.

Текущий builder формирует `https://kudago.com/public-api/v1.4/events/`, `lang=ru`, `location`, `page_size<=100`, `fields`, `expand`, `text_format=text`, UTC Unix `actual_since/actual_until`. Эти endpoint и параметры описаны в [официальной документации](https://docs.kudago.com/api/). Исправление pacing не доказывает и не обещает устранение 403.

Клиент не повторяет 403/429 в рамках запроса. 403 возвращает `kudago_http_403`; текущий импорт прерывается, Timepad в существующем цикле может продолжить работу. Следующий обычный цикл сохраняется. 429 возвращает `kudago_http_429` и устанавливает cooldown по `Retry-After`; до его истечения последующие вызовы этого клиента возвращают код без HTTP и без длительного ожидания, блокирующего Timepad. Некорректный/отсутствующий `Retry-After` даёт консервативную минутную паузу. Перезапуск сбрасывает память клиента: не использовать перезапуски для обхода ограничения.

HTTP-коды сохраняются существующими structured logs и `provider_sync_runs.error_text`; тела ответов и URL туда не добавляются. Возможны также `kudago_timeout` и `kudago_transport_error`. Автоматические redirects не выполняются. Provider-wide lock не является общей IP-квотой для других процессов или клиентов с того же адреса.

Если корректный запрос продолжает получать 403, оператору необходимо обратиться в поддержку KudaGo с временем, endpoint, безопасным набором параметров и кодом ответа, согласовав доступ. Не менять IP, токены, proxy/VPN или заголовки для обхода. Live-проверка с VPS требует отдельного разрешения.

## Переход Timepad на cities

Каждая страница и её retry получают одно URL-encoded имя города: `Москва` или `Санкт-Петербург`. Существующие `limit/skip`, `sort=+starts_at`, временное окно, fields и локальная проверка `location.city` сохранены. [Документация Timepad](https://dev.timepad.ru/api/first-request/) описывает cities отдельно от пагинации; параметр не расширяет `description_short`.

1. При первом релизе оставить `TIMEPAD_UPSERT_ONLY=true`. Автоматический процесс получает **все** страницы и выполняет insert/update, но audit run имеет `reconcile_missing=false`.
2. Человек с отдельным разрешением проверяет полноту реальной выдачи в том же окне: отфильтрованный total, все страницы, отсутствие чужого города, fetched/matched/normalized/errors и состояние каталога. Одного mock-теста или статуса succeeded недостаточно для подтверждения фактического доступа и полноты.
3. После подтверждения установить `TIMEPAD_UPSERT_ONLY=false` и пересоздать только нужный worker. Последующие полные успешные автоматические запуски снова используют существующий reconciliation. Failed/cancelled и явно ограниченные ручные `ImportPages` по-прежнему не деактивируют отсутствующие записи.
4. При сомнениях вернуть upsert-only и пересоздать worker. Запросы и обновления продолжаются по прежнему расписанию; данные не удалять.

## Санкт-Петербург

Миграция `000034_saint_petersburg_city.sql` добавляет только metadata: UUID `bf61fbf5-8c5b-53da-96c7-3560df3f8177`, имя `Санкт-Петербург`, timezone `Europe/Moscow`. При существующем СПб под другим ID или конфликте зарезервированного UUID она останавливается. `Down` сохраняет город, который может уже иметь ссылки. Production-миграция 32 (uploads) сохраняется; при интеграции аналитика и СПб получили номера 33 и 34.

Профиль соответствует `KUDAGO_LOCATION=spb` и `TIMEPAD_CITY_NAME=Санкт-Петербург`; KudaGo в отдельном сервисе не создаётся. `event-sync-timepad-spb` находится в opt-in профиле `spb`, стандартный deploy его не запускает. Moscow и SPB используют прежний общий Timepad advisory lock; согласовать разнесённое время запуска, чтобы один worker не пропускал циклы из-за занятого lock.

Только человек-оператор после согласованного релиза, backup/миграции и проверки metadata может включить ранее остановленный основной worker. Сначала проверить `KUDAGO_LOCATION=msk`, московский `EVENT_SYNC_CITY_ID`, `TIMEPAD_CITY_NAME=Москва`, `TIMEPAD_UPSERT_ONLY=true`, прежние interval/rate и `EVENT_SYNC_RUN_ON_START=false`. Не запускать второй экземпляр того же worker и не использовать ручные импорты для ускорения проверки.

```bash
dc=(docker compose --env-file .env.production -f compose.production.yaml)
"${dc[@]}" config --quiet
"${dc[@]}" up -d --no-deps event-sync
```

Дождаться очередного штатного цикла, проверить его safe logs и audit обоих провайдеров. Если KudaGo снова отвечает 403, код не исправляет доступ: сохранить безопасные сведения для поддержки. Проверить, что Timepad завершил собственный запуск независимо от этой ошибки. Разовый неуспешный/неполный импорт не разрешает включать reconciliation.

СПб включать отдельно после московской проверки и с разнесённым временем запуска:

```bash
"${dc[@]}" --profile spb up -d --no-deps event-sync-timepad-spb
```

Сначала `SPB_TIMEPAD_UPSERT_ONLY=true`; после собственной проверки полноты СПб — `false` с пересозданием сервиса. Это не меняет режим Москвы. UI выбора города остаётся отдельной задачей.

В production не печатать полный `docker compose config`, env или DSN. Причина реального Timepad failed после 117–119 страниц, текущий total с cities и доступность обоих API остаются непроверенными. Изменения кода и offline mocks не являются подтверждением устранения этих production-проблем.
